# offline-registry 使用手册

面向两类使用者：
- **维护者**：在 GitHub Actions 上为某个开源项目生成离线依赖数据包；
- **内网用户**：在内网启动离线源服务，让 Maven/npm/Go/Cargo 从中下载依赖。

---

## 一、整体原理

GitHub Actions 在联网运行器上：
1. 克隆目标项目；
2. 探测项目的语言生态（pom.xml / package.json / go.mod / Cargo.toml）；
3. 对每种生态，把依赖下载到对应的目录结构（见下表）；
4. 构建一个**通用服务镜像**（nginx 提供 Maven/Go/Node/Cargo 静态源，Verdaccio 提供 npm），推到 GHCR；
5. 把依赖数据打包成 `data-package.tar.gz`，发到 Release。

内网用户把「通用镜像」和「数据包」都拿回去：镜像负责提供协议服务，数据包解压后挂载进镜像，
即得到一个完整的内网依赖源，无需每项目重建镜像。

| 生态 | 数据目录 → 容器路径 | 服务 | 消费方协议 |
|---|---|---|---|
| Maven | `data/maven` → `/data/maven` | nginx :8081/maven | HTTP 静态 Maven 仓库 |
| npm | `data/verdaccio-storage` → `/opt/verdaccio/storage` | Verdaccio :4873 | npm registry |
| Go | `data/go` → `/data/go` | nginx :8081/go | Go module proxy |
| Node 发行包 | `data/node-dist` → `/data/node-dist` | nginx :8081/node-dist | frontend-maven-plugin |
| Cargo | `data/cargo` → `/data/cargo` | nginx :8081/cargo | cargo vendor 替换源 |

## 二、维护者：用 Actions 生成

### 前置
Fork 本仓库到自己的 GitHub 账号（数据包、镜像都会归属你的账号）。

### 触发
Actions 页 → `build-offline-registry` → Run workflow → 填 `repo_url` → 运行。

### 产物
- 通用镜像：`ghcr.io/<你的账号>/offline-registry:latest`
- 数据包：自动创建 Release，附件 `data-package.tar.gz`

### 注意事项
- 目标项目需为**开源**、可公开克隆（私有仓库请改用本地构建）。
- 构建失败（如某生态需要特殊 profile/编译参数）时，Actions 会保留已下载部分并告警，
  数据包仍会生成，内网可正常安装「能解析到的」依赖。
- Actions 运行器默认平台 linux-x64，Go/Cargo/Node 的发行包按该平台产物处理。
- 运行时长取决于项目依赖量，一般 10~40 分钟。

### 批量多项目
根目录 `projects.json`（参考 `projects.example.json`）列多个地址，按需循环调用
`bash build.sh <url>`；把多次产出的 `data/` 合并后挂载进同一容器，即可一套镜像服务多项目。

## 三、内网用户：启动与指向

### 1. 启动服务

```bash
# ① 拉镜像（离线机先 docker load 导入你保存的镜像 tar）
docker pull ghcr.io/<你的账号>/offline-registry:latest

# ② 解压数据包
mkdir -p data && tar -xzf data-package.tar.gz -C data

# ③ 用 compose 启动（已配好挂载；把 docker-compose.yml 里 OWNER 换成你的账号）
docker compose -f registry/docker-compose.yml up -d
```

验证：
```bash
curl -s http://127.0.0.1:8081/maven/ | head     # Maven
curl -s http://127.0.0.1:4873/ | head            # npm
```

### 2. 各生态指向（假设服务在 127.0.0.1，跨机请换 IP）

**Maven** `~/.m2/settings.xml`：
```xml
<mirror><id>offline-registry</id><url>http://127.0.0.1:8081/maven</url><mirrorOf>*</mirrorOf></mirror>
```

**npm**：`export NPM_CONFIG_REGISTRY=http://127.0.0.1:4873/` 或写入 `~/.npmrc`。

**Go**：`export GOPROXY=http://127.0.0.1:8081/go/cache/download,off`
- 校验和由项目 `go.sum` 保证，无需额外配置；
- 若项目需 `go get` 新版本（升级依赖），该源只含已播种版本，会失败——需回到联网机重新播种。

**Cargo**：将 `data/cargo/vendor` 拷到项目根，并把 `data/cargo/cargo-config.toml` 内容
写入项目 `.cargo/config.toml`（`directory` 填 vendor 绝对路径）。

**前端（若 Maven 工程含 Vue/前端，Node 发行包自动分发）**：
Maven 构建时追加
```
-DnodeDownloadRoot=http://127.0.0.1:8081/node-dist/ -DnpmVersion=provided
```
并确保 npm 源指向本服务（`NPM_CONFIG_REGISTRY`）。

## 四、本地手动构建（排查/私有仓库）

```bash
# 依赖：JDK21+Maven、Node、Go、Rust、Docker
bash build.sh /path/to/project ./data
PACK_TARBALL=1 bash build.sh /path/to/project ./data   # 产出 data-package.tar.gz
docker build -t offline-registry:local registry/
```

## 五、常见问题

**Q：Maven 报 `No versions available for xxx:jar:[a,b)`**
版本区间依赖需要 `maven-metadata.xml`，播种脚本已自动归一化。若为新增区间依赖，重跑播种。

**Q：npm 报 404（no such package available）**
Verdaccio 为纯离线缓存，没播种过的包无法拉取（通常是新增依赖）。重新播种或换用带上游的源。

**Q：Go 报 module 无法获取**
确认 GOPROXY 指向 `/go/cache/download`，且该模块在播种时的版本范围内。

**Q：Rust 离线为何不是「proxy 下载源」**
Rust/Cargo 生态标准离线方案是 `cargo vendor` 替换源，而非远程 proxy。工具按此实现并生成配置模板。

**Q：想新增项目或依赖**
重新运行一次 Actions（或本地 build.sh），把新数据包解压合并到 `data/` 后重启容器即可，无需重建镜像。
